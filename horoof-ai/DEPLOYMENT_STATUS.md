# Vercel deployment status

The `horoof-ai` Vercel project and a dedicated `horoof-ai` Supabase project have been created. **No application has been deployed.**

The initial private PostgreSQL schema (`migrations/001_horoof_initial.sql`) was applied and checked for RLS. It grants no browser access: authenticated server-side access and appropriate policies/API are not implemented yet. A second migration adds private PostgreSQL functions for validated letter selection and serialized buzzer claims (`migrations/002_atomic_game_actions.sql`). A rolled-back sequential database test passed; concurrent load testing is still required. A third migration adds normalized exact grading, transactional scoring, capture and Hex path detection (`migrations/003_atomic_answers.sql`). A rolled-back sequential test covered incorrect-answer handoff, correct capture, scoring and a green win. Concurrent load and broader path testing remain. These functions are not yet wired to the app. No local SQLite user accounts, sessions, documents, or games were transferred.

The running local application still uses SQLite and Socket.IO and does not use this schema. A standalone serverless API foundation is now present in `vercel-backend/`: Supabase authentication, profile, subjects, room creation/joining/lobby/start, and authenticated snapshot/select/buzz/answer routes. Expired turns are advanced on a participant snapshot via migration 004. An opt-in frontend adapter and serverless shell now connect the core flows using one-second polling; they are not deployed or browser-tested. Private text-based PDF, TXT, DOCX and PPTX document routes are implemented with PostgreSQL bytea and mock-tested; serverless OCR remains unavailable. Limited general and document-based AI draft endpoints are now implemented and tested with mocked providers; they are not full RAG and have not been tested with live credentials. Tests use mocked dependencies, not a live database or auth service. Separate rolled-back database tests cover expired turn advancement. A Vercel migration still requires an authenticated serverless API backed by PostgreSQL, atomic transactions for the buzzer and scoring, private object storage, a Vercel-compatible real-time mechanism, secrets configuration, seed/reviewed content, migrations/tests and security review. Do not deploy the current `server.js` as-is; SQLite's local filesystem is not a durable shared database and a persistent Socket.IO server is not provided by a normal serverless function.

GitHub push has not completed: the workspace has no authenticated GitHub credentials. The source ZIP excludes database files and secrets.

A tentative Vercel entrypoint (`api/index.js`) and rewrite configuration (`vercel.json`) now exist. They have not been deployed or validated on Vercel. Serverless refresh-token rotation is implemented with an HttpOnly cookie and mock-tested. Supabase email confirmation currently redirects to localhost and must be configured after an actual deployment URL is established.

## Verified PostgreSQL TLS and integration
The public Supabase Root 2021 certificate is bundled from Supabase's official SSL distribution. Its SHA-256 fingerprint is pinned in an automated test; PostgreSQL connections to Supabase enforce CA and hostname verification. The certificate expires in April 2031 and must be rotated when Supabase changes it. TLS-disabling URL parameters and unrecognized remote database hosts are rejected.

A real TLS-verified connection to the dedicated Supabase database succeeded. `test/live-postgres.js` exercised serverless game routes against real PostgreSQL: room creation, joining, 25-cell board, buzzer handoff, answer validation, capture, and score. Its test records were rolled back. Identity verification was simulated; this does not verify real Supabase Auth, browser clients, concurrency or production readiness. Run only against a test database with an authorized DATABASE_URL.

The existing database password has appeared in tool history and must be rotated before production. Do not deploy with the postgres superuser; set up and test a restricted app role and access control first. Vercel deployment, GitHub push, full localization, semantic retrieval, serverless OCR and complete live end-to-end validation remain outstanding.

## Document recovery and language progress
Migration 008 adds processing leases to the private document table. A failed upload or an extraction stuck for at least two minutes can be retried by its owner; a superseded worker cannot overwrite the new worker's results. Ready documents cannot be reprocessed through this endpoint, protecting existing source-linked drafts. This remains synchronous processing, not a durable worker queue. SQL lease recovery was checked against Supabase in a rolled-back transaction; API recovery and privacy checks use mocks. Document parsing still requires isolation and serverless OCR is unavailable.

French and Arabic dictionaries now include more navigation, game instructions, document review and consent text; stable option values keep question language separate from display translations. Some dynamic text, messages and screens remain untranslated and browser/RTL testing is still required.

## Bounded optional hybrid retrieval
The serverless sourced-draft API now offers an opt-in hybrid mode using per-request OpenAI embeddings, Unicode lexical overlap, cosine similarity and reciprocal rank fusion. It is limited to 40 passages per document and does not persist or index vectors. Separate consent is required before the query and up to 40 passages are sent for embedding; the chosen passages are then sent for draft generation. Exact-phrase mode remains available. Unit/API tests use a mock embedding provider; no real OpenAI request or relevance evaluation has been performed. This is not a scalable, indexed RAG implementation and does not validate factual correctness.

## Local browser smoke test
A Chromium test now launches a disposable SQLite server and two independent browser contexts. It passed registration, room creation/join, the 25-cell board, buzzer and correct-answer capture, mobile-width Arabic RTL, and sign-in followed by room creation after clearing cookies. This tests the bearer fallback in a normal local browser, not the user's particular embedded preview, Supabase Auth, Vercel, real mobile hardware or race conditions. Fresh SQLite starter data also corrects three problematic sample entries; existing databases are not overwritten and still need content review.

## Starter content, recovery and headers
Migration 009 was applied to the dedicated Supabase project and added a public Arabic starter collection with 28 distinct letters and matching answer initials. It enables a serverless game without a user first writing 25 questions; the questions require independent educational review.

The serverless prototype now includes password recovery requests and a reset form, with recovery tokens removed from the URL and held in memory. Both API and browser tests use a mock auth provider; real Supabase recovery email, expiry, delivery, and redirect handling remain unverified. The Supabase site URL remains localhost until deployment. Serverless responses now add a CSP that prohibits inline scripts and no-store headers for APIs; browser tests verified the shell and the inline-script restriction. Inline styles remain allowed and a security review is still required.

## Answer timer update
The answer window is now 25 seconds for the first buzzer and for each queued player after an incorrect answer or timeout. The SQLite preview was restarted with the update. Migration 010 was applied to Supabase; a rolled-back database test verified all three deadline paths. Existing active answer deadlines are not retroactively extended.

## Independent question language
Room creation now chooses Arabic, French or English question text independently of the interface locale. Manual questions record their language; local AI-reviewed questions also retain their selected language. The 5×5 Arabic-letter board still requires 25 distinct Arabic letters with approved questions in that selected language, and answers remain Arabic. The starter collection only provides Arabic questions; English/French sets must be added and reviewed before those languages are playable. Legacy SQLite questions are tagged Arabic because previous versions did not record their language and may need manual review. Migration 011 was applied to Supabase; a rollback test confirmed language-specific question selection. SQLite end-to-end and mocked serverless tests pass.

## Restricted database role foundation
Migration 012 created a NOLOGIN, non-superuser, non-BYPASSRLS `horoof_backend` group with privileges limited to the HOROOF schema and explicit policies. A rolled-back live test using SET ROLE verified room creation, question selection, buzzing and answer submission; catalog checks showed it cannot read `auth.users`. A separate login role and password have NOT been created, and pooler connectivity with that login has not been tested. These policies allow the trusted backend to access all HOROOF rows: user-level isolation remains enforced by API code, not by per-user RLS, so the backend credential must never reach a browser and further security review is essential. The previously exposed postgres password still needs rotation.

## Multiplayer interaction fixes
The local SQLite buzzer now advances an expired turn to the earliest queued player before considering a newly arriving buzz. Both frontend modes preserve a player's partially typed answer and cursor when an update re-renders the same active turn, and discard out-of-order room responses. An isolated three-player API test covers queue priority, and a two-browser smoke test verifies that typing survives another player's buzz. The local preview was restarted; this does not constitute a production concurrency/load test.
