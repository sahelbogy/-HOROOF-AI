# Serverless API foundation (not deployed)

This backend foundation has Supabase Auth registration, sign-in and sign-out handlers and authenticated PostgreSQL APIs for profile, subjects, room creation/joining, lobby actions, starting a game, snapshots, letter selection, buzzer and answers. PostgreSQL game functions enforce game-state rules and scoring. Member snapshots do not return answer keys; expired buzzer turns are advanced when a participant requests a snapshot.

It is **not yet an integrated Vercel application**. An opt-in frontend adapter and a serverless Express shell now map the core account and game flows. The adapter uses one-second polling instead of Socket.IO. The shell has a Chromium smoke test with mocked authentication and database; a full browser game against live services has not been tested. A private document API and Knowledge Hub adapter now support text-based PDF, TXT, DOCX and PPTX with a 4 MB limit; documents are currently stored as PostgreSQL bytea. OCR remains unavailable in this serverless version. A document-question generator provides exact-phrase retrieval and an optional bounded hybrid lexical/semantic retrieval mode, explicit consent, verbatim quote checks and human approval. It requires an OpenAI key; the provider has only been mock-tested. These routes are mock-tested only and parsing needs hardened isolation. Live AI validation, scalable indexed hybrid search, full account lifecycle, scalable realtime delivery, production-grade shared rate limiting, production credential configuration, reviewed seed content, deployment configuration, live-provider tests and a security review are still required. Existing tests use mocked database and authentication services. The existing preview still runs SQLite and Socket.IO, not this backend.

Never trust a client-supplied actor ID; the verified Supabase Auth token determines it. Never expose `DATABASE_URL` to the browser. Restrict database credentials, network access and server privileges before production. The Supabase confirmation-email flow and token refresh require frontend integration.

Required server-only environment variables: `DATABASE_URL` (Supabase connection pooler with TLS), `SUPABASE_URL`, `SUPABASE_ANON_KEY`. No credentials are present in this folder. Existing SQLite accounts have not been migrated.

AI quota records are retained in PostgreSQL; a retention/cleanup job and distributed abuse controls still need to be added before production. A verified quote alone does not prove an AI question or answer is correct.

A refresh endpoint and Secure, HttpOnly, SameSite=Lax refresh cookie have been added for serverless mode. The browser keeps only the short-lived access token in sessionStorage. This flow has mock tests but has not been verified in a real browser or against Supabase. Email confirmation still points to the current Supabase site URL, which must be configured for the final deployment.

### Database TLS
For Supabase database hosts, the server uses the bundled public Supabase Root 2021 CA and enforces certificate-chain and hostname verification. The certificate was obtained from `https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt` and its SHA-256 fingerprint is tested. It expires in April 2031; follow Supabase's certificate rotation guidance. Never disable certificate validation. The optional `node test/live-postgres.js` integration test requires an authorized `DATABASE_URL`; it rolls back its test records and simulates authentication.

Document extraction uses a processing token and two-minute lease. Owners can retry a failed or stale extraction; a superseded worker is prevented from updating the retry's result. Ready documents are not reprocessed, avoiding deletion of linked drafts. This is recovery for synchronous serverless execution, not a durable job queue.

### Optional hybrid retrieval
For serverless sourced drafts, the owner may explicitly choose hybrid retrieval. The search query and up to 40 document passages (at most 1,200 characters each) are sent to OpenAI's `text-embedding-3-small` model for embeddings. Lexical overlap and cosine similarity are combined using reciprocal rank fusion, then up to three selected passages are sent to the generator. Embeddings are computed afresh per request, not persisted or indexed; larger documents must use exact-phrase retrieval. Costs and external processing apply. The existing rate limit is checked before the provider call. Source quotation validation and human approval remain required. A verbatim citation is not a factual verification. OpenAI integration has not been tested with a live key.

### Password recovery and browser security
The serverless prototype supports Supabase recovery email requests and password updates using a recovery bearer. Recovery tokens received in the URL fragment are immediately removed from the address bar and held in memory for the reset form. This is mock- and browser-tested only: Supabase's site URL must be changed from localhost to the final HTTPS deployment URL, allowed redirects and SMTP must be configured, and real email delivery and link handling must be tested before launch. Recovery is not available in the SQLite preview.

The serverless shell sets a Content Security Policy which disallows inline scripts, and API responses use `Cache-Control: no-store`. Styles still require inline CSS, so these headers do not replace an XSS/security review.

Room hosts can choose Arabic, French, or English question text independently of UI locale. Questions are selected only from the room's chosen language, with 25 distinct approved letters required. Board letters and answers remain Arabic. Migration 011 adds the room language and database-side selection enforcement; the starter collection is Arabic only.

### Restricted database role foundation
Migration 012 creates a `horoof_backend` NOLOGIN group with schema-scoped privileges, explicit RLS policies and no access to `auth.users`. A rolled-back PostgreSQL role test exercises core game functions. The policies allow access to all application rows and do not enforce per-user isolation; authorization is still performed by trusted API code. No login or password is created by the migration. A properly configured login inheriting this group must be created and tested securely before deployment. Never use the exposed postgres password in production, never put database credentials in browser code or source control, and rotate the existing postgres password.
